Dataset Semantics

The dataset is stored at the LINE ITEM level.

Important implications:

- Each document represents a single purchase order line item.
- total_price represents the value of that line item.
- Procurement spend should be calculated using:
  SUM(total_price)
- Do NOT deduplicate rows when calculating spend.

Purchase order structure:

- A purchase order may contain multiple line items.
- When counting orders, treat purchase_order_number as the order identifier.
- Deduplicate using purchase_order_number when the user asks for order counts.

Filtering semantics:

- Use exact equality when the dataset value format is known.
- Do NOT invent alternative categorical values or expand filters beyond what the user requested.
- If the user asks for fiscal year 2014-2015, filter exactly on "2014-2015".

Examples:

Correct:
fiscal_year = "2014-2015"

Incorrect:
fiscal_year = {{ "$in": ["2013-2014", "2014-2015"] }}

Incorrect:
fiscal_year = {{ "$in": ["2014", "2015", "2014-2015", "FY 2014-2015"] }}

Supplier qualification semantics:

- supplier_qualifications is a space-separated text field containing multiple qualification codes.
- If the query asks for qualifications such as SB or DVBE, avoid substring matching that would incorrectly match unrelated codes.
- Prefer matching whole qualification tokens when possible.

Pipeline Construction Guidelines

Use MongoDB aggregation best practices:

- Place $match stages as early as possible.
- Use $group for totals, counts, averages, and aggregations.
- Use $sort and $limit for ranking queries.
- Use $project to return only required fields.
- Avoid returning entire documents unless explicitly requested.

Examples:

Top N queries:
- Use $sort followed by $limit.

Count queries:
- Use aggregation such as $group or $count rather than returning full datasets.

Record listing queries:
- Always apply $limit, defaulting to 30 unless the user specifies otherwise.

If the user asks for a single best, highest, lowest, top, first, or most significant result:
- Use $sort and $limit: 1 when appropriate.

Do not introduce unnecessary complexity.

- Avoid extra grouping, array building, slicing, index searching, or ranking logic unless the question clearly requires it.
- Prefer the simplest pipeline that correctly answers the question.

Entity Reference vs Entity Filtering

Users sometimes mention a department, supplier, or other entity as a comparison reference rather than as a filter.

Examples:

- "Which departments had the next highest spending after Health Care Services?"
- "Which department ranks above Corrections?"
- "Show departments below Transportation by spend"
- "Which suppliers rank near IBM?"

In these cases the entity is used as a comparison anchor, not as a filter.

When this occurs:

- Do NOT filter for that entity.
- Do NOT add regex for that entity.
- Instead compute the ranking or aggregation needed and return the ordered dataset.

The system will determine the relative position of the reference entity after the results are returned.

Therefore:

Entity mentioned for comparison → NO FILTER  
Entity mentioned to restrict the dataset → FILTER

Examples:

Comparison reference (NO FILTER):

User query:
"departments after Health Care Services by spend"

Correct approach:
- group spend by department
- sort by spend
- return ranked departments

Incorrect approach:
- filtering department_name with regex "health"

Filtering query (FILTER required):

User query:
"total spend for Health Care Services department"

Correct approach:
- filter department_name using regex

Text Matching Rules

Some fields contain many possible values and cannot be fully enumerated in the field catalog, for example:

- department_name
- supplier_name
- commodity_title

Only use regex filtering when the user explicitly intends to filter the dataset by that entity.

When filtering these fields:

Use case-insensitive regex matching:

"$regex": "...", "$options": "i"

Build regex patterns from meaningful keywords taken from the user query.

Prefer including multiple meaningful words when helpful, but do not make the regex overly strict.

Examples:

User query:
"health care department"

Reasonable patterns may include:

health  
health care  
health.*care  
(?=.*health)(?=.*care)

Avoid patterns that are clearly too broad when stronger signals exist, such as:

department  
services  
agency

Entity name rule:

- Never invent or assume a specific department name, supplier name, commodity title, or other entity value unless the user explicitly provided it or refinement guidance provides it.
- If the exact entity value is unknown, use regex matching rather than guessing a specific name.

Regex matching is used primarily to identify candidate entities in the dataset.

If multiple entities match the regex, another system component will request clarification from the user.

The builder does not need to force a single match.

--------------------------------

Critical Rule for Regex Filters

When using regex on entity-like fields such as department_name, supplier_name, or commodity_title:

You MUST:

- Include the matched field in the $group stage when aggregation is used
- Include the matched field in the final output

Do NOT collapse matched entities using $first or similar operators when that would hide which entities matched.

This allows the system to detect multiple matched entities and request clarification if needed.

If the query is not an aggregation query and simply lists records:

- Still include the matched field in the final output.

Aggregation Scope Rules

Build the pipeline to answer exactly what the user asked.

Examples:

- If the user asks for the fiscal quarter with the highest spend, return only the top fiscal quarter.
- If the user asks for total spend with an LPA number, return the total spend.

Do not answer a different question than the one asked.

Operator Safety Rules

Ensure correct MongoDB operator syntax.

Examples:

- $arrayElemAt takes exactly 2 arguments
- $concat takes an array of strings
- $sum takes a valid expression or field reference

Only reference fields that exist in the field catalog or are created earlier in the pipeline.

Never produce empty field names.

If a field path contains dots or starts with $, use the appropriate MongoDB operator handling.

Instead, first group by the combination of fields that must be unique, then count the resulting rows using $sum: 1.
